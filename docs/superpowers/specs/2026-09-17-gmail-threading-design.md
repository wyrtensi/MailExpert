# Цепочки писем Gmail по X-GM-THRID

Статус: решения приняты 2026-09-17. PR A слит (#52). План PR B в `docs/superpowers/plans/2026-09-17-gmail-threading-pr-b-provider-id-backfill.md`, план PR C пишется после его слияния.

Источник идей: разбор движка цепочек форка Inboxora (TypeScript, без общей истории с MailExpert). Код не переносится, только решения. Первый шаг разбора, привязка цепочки к ящику, уже сделан в #50.

## Цель

Письма ящика Gmail группируются в цепочки так же, как в веб-интерфейсе Gmail: по номеру цепочки Gmail (`X-GM-THRID`). Причина склейки видна администратору, а переход для каждого ящика можно заранее оценить и откатить.

## Как сейчас

- `messages.thread_id` вычисляет `computeThreadId` (`backend/src/services/imapManager.js:1279`):
  1. цепочка `References` и `In-Reply-To` внутри ящика;
  2. если предок ещё не синхронизирован, временный корень `thread_id = References[0]`;
  3. если заголовков нет, самое раннее письмо ящика с той же нормализованной темой за 90 дней;
  4. иначе собственный `Message-ID`.
- `thread_key` — хранимая вычисляемая колонка `COALESCE(thread_id, id::text)` с четырьмя индексами (`0009_thread_key_column.sql`). Каждое изменение `thread_id` переписывает строку и эти индексы.
- Вычисление вызывается в живом синке (`:3503`), фоновой догрузке (`:4173`), записи копии в «Отправленных» после отправки (`:4796`) и записи черновика.
- `ON CONFLICT` при повторном получении строки заменяет `thread_id`, только если строка была корнем самой себя (#378, `:3567`).
- `rerootThreadChildren` (`:1268`) переносит детей временного корня на настоящий, когда тот приходит.
- FETCH-запросы не просят номер цепочки. imapflow 1.7.8 на Gmail всегда запрашивает `X-GM-MSGID` (приходит как `emailId`) и по флагу `threadId: true` запрашивает `X-GM-THRID` (`node_modules/imapflow/lib/commands/fetch.js:98-113`). `emailId` сейчас выбрасывается.
- Профиль Gmail определяется по хосту `*.gmail.com` / `*.googlemail.com` (`providerProfile`, `:1155`). У Gmail пропускаются `All Mail`, `Starred`, `Important`; синхронизируются INBOX, `Sent Mail`, папки-ярлыки, `Trash`, `Spam`.

## Проверенные риски

| Риск | Что проверено | Итог |
| --- | --- | --- |
| Плагины хранят ключи цепочек | GTD (`gtdTransitions.js`, `gtdSections.js`, `hooks.js`), `labelsRead.js`, `mailAccess.js`, таблица `plugin_data`, `plugin_annotations` | Ключи вычисляются на лету из `messages`, нигде не хранятся. Смена формата ключа их не ломает |
| Фронтенд хранит ключи цепочек | `localStorage`, `pendingDeletes.js`, кэш `threadMessages` | Только в памяти, кэш сбрасывается при смене ящика и режима. Ключ используется как непрозрачная строка, `encodeURIComponent` в `api.getThread` пропускает `gmail:` |
| imapflow не умеет X-GM-THRID | исходник fetch и разбор ответа в `tools.js:740-755` | Умеет: `threadId: true`, результат в `msg.threadId`, `X-GM-MSGID` в `msg.emailId` |
| Копия в «Отправленных» после отправки снова станет отдельной цепочкой (#378) | путь `upsertSentMessageRecord` | Ответ наследует `gmail:`-ключ предка через поиск по `References`. Новая переписка получает свой `Message-ID`, пока синк `Sent Mail` не принесёт номер Gmail. Правило `ON CONFLICT` должно давать `gmail:`-ключу побеждать любой другой, иначе такая копия останется отдельно |
| `rerootThreadChildren` перезапишет `gmail:`-ключи RFC-корнем | условие `thread_id = $3` | Детям с `gmail:`-ключом RFC-корень не подходит (`$3` — `Message-ID`), но для ящика в режиме Gmail перенос нужно явно выключить, чтобы не смешивать режимы |
| Пересчёт миллионов строк блокирует базу | хранимая `thread_key` и 4 индекса | Реален. Только фоновые пачки по 2-5 тысяч строк с паузами и повтором без эффекта (`WHERE thread_id IS DISTINCT FROM ...`), индексы через `CREATE INDEX CONCURRENTLY`. Замер на синтетических данных нужен до выпуска: требует Docker |
| Лимиты Gmail при догрузке номеров | 15 сессий на ящик, общий фоновый бюджет `maxBackgroundConnections: 6` | Догрузка идёт через тот же фоновый бюджет, лёгкий `UID FETCH <диапазон> (UID X-GM-THRID X-GM-MSGID)` без конвертов и тел, диапазонами UID, не параллельно с первичной догрузкой ящика |
| Смесь ключей в одном ящике расколет цепочки | переключение до окончания догрузки | Флаг режима на ящик. Переключение только после догрузки всех папок ящика |
| Номера цепочек Gmail разных ящиков совпадут | `X-GM-THRID` уникален в пределах аккаунта Gmail | Ключ `gmail:<thrid>` плюс цепочки уже ограничены ящиком (#50). В общем «Входящие» списке группировка идёт по `thread_key` без ящика: совпадение номеров у двух ящиков теоретически склеит строки. Группировку списка нужно тоже вести по `(account_id, thread_key)` |
| Поведение в общем «Входящие» меняется | `listMessages` группирует по `thread_key` | Сейчас одна переписка, пришедшая в два ящика, в общем «Входящие» одна строка (одинаковый RFC-ключ). С ключами Gmail это две строки, по одной на ящик. Это решение пользователя (вопрос 2) |
| Конфликты при синке с upstream | `imapManager.js` > 6000 строк, частые переносы | Логику держать в `backend/src/services/threading/`, в `imapManager.js` только короткие вызовы |
| Удаление склейки по теме расклеит часть цепочек | письма без `References`, склеенные только по теме | Реален, масштаб неизвестен. Пробный пересчёт показывает число затронутых строк до переключения |

## Дизайн

### PR A. Номера Gmail при синке

- Миграции `0060_message_provider_ids.sql` (`messages.provider_thread_id`, `messages.provider_message_id`, nullable без default) и `0061_message_provider_thread_index.sql` (индекс `(account_id, provider_thread_id)` через `CONCURRENTLY`). `threading_reason` и `email_accounts.thread_mode` / `thread_backfill` появятся в PR B и C, где используются.
- Склейка по теме за 90 дней убирается из `computeThreadId` для всех ящиков (решение 1). Новые письма без `References` и `In-Reply-To` становятся отдельными цепочками; старые склейки разбирает пересчёт из PR C.
- Для профиля Gmail `fetchQuery` и `bfQuery` получают `threadId: true`. Живой синк, догрузка и `ON CONFLICT` записывают `provider_thread_id` и `provider_message_id`. `thread_id` не меняется.
- Модули `services/threading/threadId.js` (`computeThreadId` без склейки по теме, перенесён из `imapManager.js`) и `services/threading/providerIds.js` (`gmailProviderIds`).
- Для пользователя меняется только одно: новые письма без заголовков цепочки больше не склеиваются по теме.

### PR B. Догрузка номеров для старых писем

- Таблица `provider_id_backfill` (миграция `0062`): по ящику курсор `{ lastUid, uidValidity }` на папку, `finished_at`, `error`. Состояние «идёт» хранится только в памяти процесса, поэтому падение не оставляет ящик «зависшим».
- Модули `services/threading/providerIdBackfill.js` (план и проход) и `providerIdBackfillStore.js` (прогресс). Проход берёт из базы строки без номеров выше курсора пачками по 500 UID, запрашивает `UID FETCH <набор> (UID X-GM-MSGID X-GM-THRID)` и пишет номера одним `UPDATE ... FROM unnest(...)`. Курсор сохраняется после каждой пачки. `thread_id` не меняется.
- Запуск только для ящиков Gmail: после полной догрузки, при подключении ящика, у которого полная догрузка не нужна, через минуту после записи копии в «Отправленных» или черновика (синк не перезапрашивает уже сохранённый UID), и планировщиком раз в 10 минут, пока последний проход не закончился чисто. Соединение берётся из общего фонового бюджета хоста и только если есть что запрашивать.
- Статус в админке у ящика: не начато, идёт (процент), приостановлено, готово, ошибка. Событие WebSocket `provider_ids_backfill`.
- При старте сервер проверяет `indisvalid` индекса `idx_messages_provider_thread` и пишет предупреждение, если индекс невалиден или отсутствует. Переключение на цепочки Gmail в PR C требует валидного индекса.

### PR C. Группировка по цепочкам Gmail и диагностика

- `computeThreadId` для ящика в режиме `gmail`: есть номер → `gmail:<thrid>`, причина `gmail-thrid`; нет номера → RFC-цепочка без склейки по теме, причины `rfc-root`, `rfc-ancestor`, `rfc-provisional`, `new-root`.
- `ON CONFLICT`: `gmail:`-ключ из синка заменяет любой не-`gmail:` ключ строки. Тест на копию «Отправленных» новой переписки.
- `rerootThreadChildren` не вызывается для ящиков в режиме `gmail`.
- `listMessages` и счётчики цепочек группируют по `(account_id, thread_key)`.
- Переключение ящика (админка, кнопка у ящика, доступна после завершения догрузки):
  1. пробный пересчёт: сколько строк сменят `thread_id`, сколько цепочек разделится или объединится, сколько писем держались только на склейке по теме. Чистый SQL сравнением `thread_id` с `'gmail:' || provider_thread_id`, без записи;
  2. включение: `thread_mode = 'gmail'` и фоновый пересчёт `thread_id` пачками;
  3. откат: `thread_mode = 'rfc'` и тот же пересчёт по RFC-заголовкам (`in_reply_to`, `thread_references` сохраняются).
- Пересчёт в режиме `rfc` доступен и для ящиков не на Gmail: он разбирает цепочки, склеенные по теме до PR A.
- Диагностика в админке: по письму или цепочке показать `Message-ID`, `In-Reply-To`, `References`, номер Gmail, причину, папки.
- Журнал: включение и откат пишутся в `mailbox_audit_log` (`mailbox.threading_changed`).

### Позже, отдельной серией. Чтение всей переписки

Панель чтения цепочки целиком поверх `/mail/thread` и `/messages/:id/body`: последнее письмо раскрыто, тела грузятся лениво, цитаты свёрнуты. Отдельная настройка (решение 3).

## Что не берём

- Модель Inboxora с логическими письмами, алиасами, доказательствами и неразрешёнными ссылками: второй источник истины рядом с `thread_key`.
- `Thread-Index` Outlook.
- Ручное объединение и разделение цепочек: расходится с веб-Gmail, в интерфейсе Inboxora его нет.
- Номера цепочек не-Gmail серверов (`OBJECTID`/`THREADID`): ящики не на Gmail остаются в режиме `rfc`.

## Решения

1. Склейка по теме не нужна ни в одном режиме: убирается для всех ящиков.
2. Одна переписка в двух ящиках — две строки в общем «Входящие», по одной на ящик.
3. Панель чтения всей переписки — отдельной серией после этой.
4. Замер пересчёта и полный прогон тестов бэкенда — локально в Docker.
