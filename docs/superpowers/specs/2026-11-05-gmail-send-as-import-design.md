# Импорт алиасов Gmail (send-as) в поле "От"

Дата: 2026-11-05. Статус: черновик, ждёт согласования владельцем (владелец).

## Зачем

Клиенты работают через адреса `имя_фамилия@example.com`. Каждый такой адрес - алиас
Google Workspace на одном из трёх ящиков: `team@example.com` (23 алиаса), `science@example.com` (26),
`post@example.com` (30). Для каждого алиаса в Gmail ящика-владельца уже настроен Send mail as.
Входящие на алиас падают в ящик-владелец.

Владелец подключил `team@example.com` к панели <PANEL_HOST> как Gmail через OAuth. Письма видны, но
отвечать с алиасов нельзя: в `account_aliases` у ящика пусто, а завести ~79 алиасов руками и
поддерживать их после каждого изменения в Gmail никто не будет.

Цель: панель сама знает алиасы Gmail-ящика, сотрудник видит, на какой адрес пришло письмо, и
"Ответить" уходит с этого адреса.

## Решения владельца

- Отправитель при ответе: `Name Surname <username@example.com>`, то есть имя и адрес алиаса.
- В списке писем у входящего, пришедшего на алиас, видна плашка с адресом получателя.
- "Ответить" использует алиас, на который пришло письмо.
- Изменения алиасов в Gmail должны появиться в панели в течение часа. Меняются они редко.
- Источник истины - Gmail. Ручные правки импортированного алиаса в панели перезаписываются.
- Делаем без участия автора форка.
- Не сейчас: отдельный виртуальный ящик на каждый алиас.

## Что уже есть в коде (main @ 78895951)

- Gmail-ящики подключены через Google OAuth со scope `https://mail.google.com/`. Отправка идёт через
  Gmail API (`backend/src/services/gmailApiSender.js`), значит токен ящика годится и для
  `GET https://gmail.googleapis.com/gmail/v1/users/me/settings/sendAs`. Повторного согласия не нужно,
  Gmail API в проекте Google Cloud включён.
- Алиасы: таблица `account_aliases` (`backend/migrations/0001_baseline.sql`: `name`, `email`,
  `reply_to`, `signature`), сервис `backend/src/services/accountAliases.js`, роуты
  `/api/accounts/:id/aliases` в `backend/src/routes/accounts.js`. Поле "От" строится из ящиков и их
  алиасов (`frontend/src/utils/defaultSender.js`).
- При ответе алиас уже выбирается автоматически: `frontend/src/utils/replyAlias.js` (`pickReplyAlias`)
  сравнивает To/Cc/`delivery_addresses` письма с алиасами ящика. Как только алиасы появятся в
  `account_aliases`, "Ответить" начнёт отвечать с них без новой кнопки.
- Очередь заданий: `registerJobKind` в `backend/src/services/jobQueue.js`, примеры -
  `services/mailNode/nodeChecks.js`, `services/accessSync/actions.js`.
- Полоса над открытым письмом показывает `via` (`frontend/src/utils/mailboxBanner.js`) по
  `delivery_addresses` (Delivered-To и подобные). В строке списка есть только `DirectionBadge`.

## Что делаем

### 1. Пометка источника алиаса

Миграция: у `account_aliases` появляется источник (`manual` по умолчанию / `gmail`) и, для
импортированных, ключ записи в Gmail (адрес `sendAsEmail`). Существующие строки остаются `manual`.

### 2. Синхронизация send-as

Для каждого Gmail-ящика, подключённого через Google OAuth:

- Читаем `users.settings.sendAs.list`.
- Берём записи с `verificationStatus = accepted` и без `isPrimary`. Записи `pending` пропускаем.
- Импортированный алиас: `email` = `sendAsEmail`, `name` = `displayName` (пустой - локальная часть
  адреса), `reply_to` = `replyToAddress`, `signature` = `signature` (через тот же
  `sanitizeSignature`).
- Запись есть в Gmail и нет в панели - создаём. Есть в обоих - обновляем поля из Gmail. Есть в панели
  как `gmail`, но пропала из Gmail - удаляем.
- Алиасы `manual` синхронизация не трогает никогда. Если ручной алиас совпадает по адресу с send-as
  из Gmail - решение за исполнителем, но без дублей в "От" (например, перевести его в `gmail`).
- Когда запускается: сразу после подключения или переподключения Google-ящика; фоном раз в час для
  всех таких ящиков (задание в очереди); по кнопке.
- Ошибка Google (протухший токен, 403, 429) не должна удалять алиасы: при неудачном чтении список не
  меняем. Ящик в состоянии "нужно переподключить" пропускаем.
- Каждое изменение (создан, обновлён, удалён) - в журнал (`services/auditLog.js`), актор - система или
  пользователь, нажавший кнопку.
- Токены не попадают в логи, ответы API и тексты ошибок.

### 3. Интерфейс ящика

- В настройках Gmail-ящика, в блоке алиасов, кнопка "Обновить алиасы из Gmail" с результатом
  (сколько добавлено, обновлено, удалено) и временем последней синхронизации.
- У импортированного алиаса поля имени, адреса, Reply-To и подписи только для чтения, с пояснением
  "Синхронизируется из Gmail, правьте в Gmail". Удалить его в панели нельзя - удаляется в Gmail.
  Это решение руководителя: иначе правка молча пропадёт при следующей синхронизации.
- Ручные алиасы работают как раньше.

### 4. Плашка получателя в списке писем

- В строке списка у входящего письма показываем адрес, на который оно пришло, если это не основной
  адрес ящика.
- Gmail обычно пишет в Delivered-To основной адрес ящика, а не алиас (проверить на живом письме в
  `team@`). Поэтому плашка показывает адрес, который `pickReplyAlias` выбрал бы для ответа, то есть
  текущий алиас этого ящика из `delivery_addresses`/To/Cc.
- Плашка и "От" при ответе обязаны показывать один адрес: выбор адреса выносится в одну общую
  функцию, её используют и плашка, и `pickReplyAlias`. Решение руководителя: адрес, которого нет среди
  текущих алиасов ящика, плашку не получает (у всех трёх ящиков один домен, и правило "любой
  адрес на домене" показывало бы адреса соседних ящиков, с которых отсюда не ответить). У старых писем
  удалённых клиентов плашка пропадёт, это приемлемо.
- Импортированный алиас при обновлении сохраняет свой `id` (обновление на месте, не удалить и
  создать), чтобы открытые черновики и выбор "От" не ломались.
- Если при отправке `aliasId` не найден (алиас удалили, пока было открыто окно письма), сейчас
  `backend/src/routes/send.js` молча отправляет с основного адреса. Меняем: отправка отклоняется с
  понятной ошибкой, сотрудник выбирает "От" заново.
- Письмо, где алиас был только в Bcc, распознать нельзя: плашки нет, ответ с основного адреса.
  Это известное ограничение.
- Плашка помещается в узкую строку (мобильный вид, узкая колонка): в компактном режиме -
  сокращённо, полный адрес в `title`/`aria-label`, как у `DirectionBadge`.

### 5. Документация и демо

- Руководство пользователя (раздел про алиасы и "От") и описание для оператора - по-русски.
- Новые строки интерфейса - в `locales/en.json` и `ru.json`.
- Новые API-пути - ответ в `frontend/src/demo/`.

## Не делаем

- Виртуальный ящик на каждый алиас.
- Запись алиасов в Gmail или Google Admin из панели: панель только читает.
- Синхронизацию для не-Gmail ящиков.
- Admin SDK Directory API (`users.aliases.list`): нужен доступ администратора Workspace, а имён,
  подписей и статуса send-as там нет.

## Провал, даже если технически работает

- Ответ клиенту ушёл с `team@example.com` вместо его алиаса.
- Временная ошибка Google стёрла алиасы из панели.
- Плашка показывает один адрес, а "От" при ответе - другой.
