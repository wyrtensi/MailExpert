# Общие ящики и вход только через Google

> Статус: дизайн одобрен 2026-09-15, реализация не начата. Работы по нескольким Google OAuth-приложениям (PR 2–5 из `2026-09-15-google-multi-app-design.md`) приостановлены до PR 3 этого документа и затем переписываются под общий список ящиков.

## Зачем

Сейчас каждый почтовый ящик принадлежит одному пользователю MailExpert (`email_accounts.user_id`), а MVP обходит это общей рабочей учётной записью, под которой входят все менеджеры. Из-за этого нельзя понять, кто из менеджеров что сделал, нельзя отключить одного менеджера, не меняя общий пароль, а выход одного менеджера разрывает IMAP-соединения у всех.

Новая модель:

- ящики обслуживает сервер, они общие для всей установки;
- в MailExpert входят только одобренные пользователи и только через Google;
- любой вошедший пользователь видит все ящики и полностью управляет ими: добавляет, переподключает, удаляет, меняет настройки, читает и отправляет письма;
- у администратора остаются только системные настройки;
- действия с ящиками, отправка и удаление писем записываются в журнал с автором.

## Принятые решения

- Разграничения доступа по ящикам нет. Доступ к установке — это и есть доступ ко всем ящикам.
- Одобрение пользователя — строка в `users`, которую создаёт администратор, или email из `BOOTSTRAP_ADMIN_EMAILS`. Статуса «ожидает одобрения» нет.
- Два входа в одно приложение: через Cloudflare Access и прямой вход через Google на отдельном хосте без Cloudflare. Прямой вход нужен там, где хосты Cloudflare недоступны без VPN.
- Пароли, MFA, OIDC, регистрация, приглашения и сброс пароля в этом режиме не используются.
- Статус пользователя проверяется в базе на каждом запросе и не кешируется в сессии: пользователь видит все ящики, поэтому отзыв доступа держится только на этой проверке.
- Правила, блок-лист, контакты, отложенные письма, категоризация и обучение спам-фильтра — общие.
- Личными остаются только push-подписки, настройки интерфейса (`users.preferences`, кроме интервалов синхронизации), PIN экрана блокировки и личная интеграция Todoist.
- Синхронизация списка пользователей с политикой Cloudflare Access делается отдельным PR после входа.

## Не входит

- Доступ к отдельным ящикам и роли уровнем ниже администратора.
- Личный порядок ящиков и личный выбор ящиков для общей ленты: `sort_order` и `include_in_unified_inbox` остаются полями ящика.
- Журнал перемещений, прочтений и изменений флагов; автоочистка журнала.
- Встроенный CardDAV-сервер для телефонов в режиме входа через Google: у клиентов нет пароля для Basic Auth.
- Управление доменными правилами (`email_domain`) политики Cloudflare Access из MailExpert.
- Вызов Cloudflare API для принудительного завершения сессий.

## Режимы входа

`AUTH_MODE` задаёт режим:

- `local` (по умолчанию) — текущий вход: пароль, MFA, OIDC, регистрация и приглашения. Остаётся для разработки и установок, совместимых с upstream.
- `google` — вход только одобренных пользователей через Cloudflare Access или прямой Google-вход.

В режиме `google` сервер не стартует, если не задан ни один из входов: ни пара `CF_ACCESS_ISSUER` + `CF_ACCESS_AUDIENCE`, ни пара `AUTH_GOOGLE_CLIENT_ID` + `AUTH_GOOGLE_CLIENT_SECRET`.

### Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `AUTH_MODE` | `local` или `google`. |
| `CF_ACCESS_ISSUER` | `https://<TEAM>.cloudflareaccess.com`, без завершающего `/`. |
| `CF_ACCESS_AUDIENCE` | AUD-тег Access-приложения. |
| `AUTH_GOOGLE_CLIENT_ID`, `AUTH_GOOGLE_CLIENT_SECRET` | OAuth-клиент для входа в MailExpert, scope `openid email`. Не связан с Google-приложениями для подключения Gmail-ящиков. Можно использовать тот же клиент, что стоит за Google IdP в Cloudflare Access, добавив ему redirect URI прямого хоста. |
| `BOOTSTRAP_ADMIN_EMAILS` | Email администраторов через запятую, в нижнем регистре. |
| `APP_URL` | Основной публичный адрес. |
| `APP_ALT_URLS` | Дополнительные публичные адреса через запятую, например прямой хост. |

### Проверка личности

Один middleware стоит перед `/api`, `/oauth` и подключением WebSocket (`/ws`). Nginx фронтенда уже проксирует эти пути в бэкенд.

1. **Вход через Cloudflare.** Если заданы `CF_ACCESS_ISSUER` и `CF_ACCESS_AUDIENCE` и в запросе есть `Cf-Access-Jwt-Assertion`, токен проверяется библиотекой `jose`: RS256, `issuer`, `audience`, ключи из `<issuer>/cdn-cgi/access/certs`. Набор ключей кешируется на 10 минут; если обновить его не удалось, последний полученный набор используется до 24 часов. Идентичность — claim `email` в нижнем регистре. Невалидный токен — 401.
2. **Прямой вход.** `GET /oauth/login/google` создаёт state и PKCE (как `oauthState` для ящиков, провайдер `auth-google`) и отправляет в Google со scope `openid email`. `GET /oauth/login/google/callback` обменивает код, проверяет ID token (`iss`, `aud`, `email_verified = true`) и находит пользователя по email. Redirect URI строится из origin запроса и допускается, только если origin есть в `APP_URL` или `APP_ALT_URLS`.
3. **Без Cloudflare-заголовка** запрос идентифицируется по сессии, созданной одним из входов. Если без настроенного Cloudflare кто-то присылает `Cf-Access-Jwt-Assertion`, заголовок игнорируется.
4. **Пользователь** ищется по `lower(users.email)`.
   - Вход через Cloudflare: если строки нет, пользователь создаётся автоматически, потому что членство в политике Access и есть одобрение.
   - Прямой вход: неизвестный email получает 403 `not_allowed`. Исключение — email из `BOOTSTRAP_ADMIN_EMAILS`: такой пользователь создаётся.
   - Email из `BOOTSTRAP_ADMIN_EMAILS` при каждом входе получает `is_admin = true`.
5. **Сессия.** Если в сессии записан другой пользователь, чем в проверенном токене, сессия пересоздаётся (`req.session.regenerate`). После прямого входа сессия тоже пересоздаётся. В режиме `google` срок жизни сессии — 7 дней.
6. **Статус.** `requireAuth` уже читает `users` на каждом запросе; условие дополняется `disabled_at IS NULL`. Отключённый пользователь получает 403 `user_disabled`, его сессия уничтожается.

Отключение пользователя закрывает все его WebSocket-соединения (`imapManager.closeUserSockets(userId)`). Проверка при подключении WebSocket выполняет те же шаги 1, 3, 4 и 6.

### Выход

- Хост за Cloudflare: сессия уничтожается, клиент уходит на `/cdn-cgi/access/logout`.
- Прямой хост: сессия уничтожается, клиент уходит на `/login`.

Хост определяется по `Cf-Access-Jwt-Assertion` в запросе на выход.

### Что отключается в режиме `google`

- Маршруты входа по паролю, MFA/TOTP, OIDC, регистрации, приглашений, смены и сброса пароля отвечают 404.
- Экран входа показывает только кнопку «Войти через Google». Если пользователь пришёл через Cloudflare, экран входа не показывается.
- Встроенный CardDAV-сервер не монтируется.
- Резервная отправка системных писем (сброс пароля, приглашения) через рабочие почтовые ящики убирается в обоих режимах: системные письма уходят только через системный SMTP.

### Пользователи

Миграция: `users.email VARCHAR(255)` с уникальным индексом по `lower(email)`, `users.disabled_at TIMESTAMPTZ`, `users.disabled_by UUID REFERENCES users(id) ON DELETE SET NULL`. У существующих пользователей `email` пустой; для входа администратор заполняет его в панели.

Администратор в панели:

- добавляет пользователя по email (`username` = email, пароль пустой);
- отключает и включает пользователя;
- назначает и снимает права администратора;
- удаляет пользователя. Ящики и записи журнала при этом остаются.

Нельзя отключить, удалить или лишить прав последнего активного администратора и любой email из `BOOTSTRAP_ADMIN_EMAILS`.

## Сервер обслуживает ящики

- При старте сервера все включённые IMAP-ящики ставятся в очередь и подключаются по `IMAP_CONNECT_CONCURRENCY` штук одновременно (по умолчанию 3). Это не ограничение числа ящиков: подключаются все, очередь только растягивает логины во времени. `IMAP_MAX_PERSISTENT_PER_HOST` не меняется.
- Вход, выход, открытие WebSocket, отключение и удаление пользователя не подключают и не отключают ящики. Вызовы `connectAllForUser` из `auth.js`, `oidc.js`, `websocket.js` и `disconnectUser` из выхода и удаления пользователя убираются.
- Восстановление упавших соединений остаётся внутри `imapManager`, как сейчас.
- `POST /api/mail/sync` и `POST /api/mail/sync-folders` принимают только конкретный ящик. Без `accountId` — 400 `account_required`; фронтенд в том же PR всегда передаёт ящик. Повторный запрос по ящику, у которого синхронизация уже идёт или завершилась меньше 15 секунд назад, не запускает новую и отвечает `{ ok: true, skipped: true }`.
- Кнопка «Переподключить» (`POST /api/accounts/:id/reconnect`) действует на один ящик; повторное нажатие во время подключения ничего не запускает.
- Интервалы синхронизации писем и структуры папок — системные настройки `sync_interval_sec` и `folder_sync_interval_sec` в `system_settings`. Меняет администратор, по умолчанию 60 секунд для писем и 30 минут для папок (`DEFAULT_FOLDER_SYNC_INTERVAL_MS`). Поля `syncInterval` и `folderSyncInterval` из личных настроек убираются. Миграция берёт значения пользователя, которому принадлежит больше всего ящиков, если они заданы.

## Общие данные

Миграция одна, выполняется в PR 3 вместе со снятием фильтра по владельцу во всех запросах.

| Данные | Было | Стало |
| --- | --- | --- |
| Ящики `email_accounts` | `user_id NOT NULL`, каскадное удаление с пользователем | `added_by UUID REFERENCES users(id) ON DELETE SET NULL`, заполняется из `user_id`; `user_id` удаляется |
| Правила `inbox_rules` | `user_id`, `account_id` может быть NULL («все мои ящики») | `account_id NOT NULL`, `created_by ... ON DELETE SET NULL`. Правило с `account_id IS NULL` копируется на каждый ящик своего владельца вместе со строками `inbox_rule_forwards`; исходная строка удаляется |
| Блок-лист `block_list` | `(user_id, email_address)` | `(account_id, email_address)`, уникальность по паре. Каждая запись копируется на каждый ящик своего владельца, дубли отбрасываются |
| Адресные книги и контакты | `address_books.user_id`, `contacts.user_id` | Колонки удаляются. Уникальность книг — по `name`: при совпадении имён книга переименовывается в `<name> (<username>)`. Миграция создаёт общую книгу «Контакты» для автоконтактов |
| Синхронизация с внешним CardDAV | `user_integrations` с `provider = 'carddav'` у пользователя | Одна системная настройка. Если настройка была у нескольких пользователей, остаётся обновлённая последней; книги остальных становятся обычными книгами без синхронизации |
| Источники категорий `category_list_sources` | `user_id` | Колонка удаляется, уникальность по `(source_type, value)`, дубли отбрасываются |
| Общий переключатель категоризации | `users.preferences` | Системная настройка `categorization_enabled`; включена, если была включена у любого пользователя. Переключатель на ящике остаётся |
| Отложенные письма `snoozed_messages` | `user_id` | `snoozed_by ... ON DELETE SET NULL` |
| Обучение спам-фильтра `spam_training_log` | `user_id` | `trained_by ... ON DELETE SET NULL`, индексы по пользователю заменяются индексами по ящику |
| Push-подписки, `users.preferences`, PIN экрана блокировки, Todoist, данные плагинов с `owner_id` | личные | без изменений |

Изменения в коде:

- Во всех маршрутах и сервисах условие `a.user_id = $n` или `user_id = $n` у ящиков, писем, правил, блок-листа, контактов, категорий и отложенных писем убирается. Проверка «ящик или письмо принадлежит пользователю» становится проверкой существования.
- API плагинов `services/mailAccess.js`: `loadOwnedMessage` и `getOwnedAccount` проверяют существование, `listUserAccounts` возвращает все ящики. Имена функций сохраняются, комментарии описывают новую модель.
- События ящиков из `imapManager.broadcast` получают все подключённые WebSocket-клиенты. События, адресованные одному пользователю (например, изменение его настроек), остаются адресными.
- Push о новых письмах получают все активные пользователи с подпиской. Счётчик непрочитанных считается по всем включённым ящикам.
- Автоконтакты из входящих пишутся в общую книгу «Контакты».
- Диагностический отчёт строится по всем ящикам.
- Удаление ящика (`DELETE /api/accounts/:id`) доступно любому вошедшему пользователю.

Фронтенд в том же PR меняется ровно настолько, чтобы работали правила и блок-лист в разрезе ящика, общие контакты и системные интервалы.

## Журнал

Миграция: таблица `mailbox_audit_log`.

```sql
CREATE TABLE IF NOT EXISTS mailbox_audit_log (
  id            BIGSERIAL PRIMARY KEY,
  occurred_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  actor_user_id UUID REFERENCES users(id) ON DELETE SET NULL,
  actor_email   VARCHAR(255),
  account_id    UUID REFERENCES email_accounts(id) ON DELETE SET NULL,
  account_email VARCHAR(255),
  action        VARCHAR(64) NOT NULL,
  details       JSONB NOT NULL DEFAULT '{}'
);
CREATE INDEX IF NOT EXISTS idx_mailbox_audit_occurred ON mailbox_audit_log (occurred_at DESC, id DESC);
CREATE INDEX IF NOT EXISTS idx_mailbox_audit_account ON mailbox_audit_log (account_id, occurred_at DESC);
CREATE INDEX IF NOT EXISTS idx_mailbox_audit_actor ON mailbox_audit_log (actor_user_id, occurred_at DESC);
```

`actor_email` — email пользователя, или `username`, если email пуст.

| `action` | Когда | `details` |
| --- | --- | --- |
| `mailbox.added` | Ящик создан вручную, как доменный или через OAuth | `{ protocol, oauthProvider }` |
| `mailbox.reconnected` | OAuth-авторизация ящика выдана заново | `{ oauthProvider }` |
| `mailbox.deleted` | Ящик удалён | `{}` |
| `mailbox.connection_changed` | Изменены сервер, порт, TLS, логин, пароль или OAuth-приложение | `{ fields: [...] }`, только имена полей |
| `mailbox.enabled`, `mailbox.disabled` | Ящик включён или выключен | `{}` |
| `message.sent` | Письмо принято SMTP-сервером | `{ messageId, to: [...], cc: [...], bcc: [...] }` |
| `message.deleted` | Пользователь удалил письмо: в корзину или навсегда | `{ messageId, folder, from, permanent }` |
| `user.added`, `user.deleted`, `user.enabled`, `user.disabled`, `user.admin_changed` | Действия администратора с пользователями | `{ email, isAdmin }` |

Правила:

- Пишутся только действия пользователей. Синхронизация и правила входящих журнал не пишут.
- Массовое удаление пишет запись на каждое письмо.
- Тема, текст и вложения писем, пароли, токены и секреты в журнал не попадают.
- Запись журнала не должна ломать действие: ошибка вставки логируется без содержимого, действие завершается.

API: `GET /api/admin/audit?account=&user=&action=&from=&to=&before=` (только администратор), по 100 записей, курсор по `(occurred_at, id)`.

## Синхронизация с Cloudflare Access

Отдельный PR после входа.

- Источник правды — активные пользователи MailExpert. Воркер приводит список `include` Allow-политики Access-приложения в соответствие с ними.
- Учётные данные (account id, app id, policy id, API-токен с правом «Access: Apps and Policies — Edit» на один аккаунт) хранятся в `system_settings` зашифрованными; токен только записывается и никогда не показывается.
- Политика читается и записывается целиком через `PUT`. Для reusable-политики используется эндпоинт `/access/policies/{id}`, для политики приложения — `/access/apps/{app}/policies/{id}`. Read-only поля (`id`, `uid`, `created_at`, `updated_at`) удаляются перед записью.
- Трёхсторонняя сверка с сохранённым baseline:
  - email удаляется из политики, только если MailExpert сам его туда добавил;
  - чужие правила, группы и `email_domain` сохраняются;
  - email, удалённый в Cloudflare, отключает пользователя в MailExpert, если его всё ещё не пропускает `email_domain`-правило без `exclude`.
- `BOOTSTRAP_ADMIN_EMAILS` никогда не удаляются из политики и не отключаются.
- Пустой итоговый `include` не записывается.
- Прогон, который отключил бы больше `ACCESS_SYNC_MAX_DISABLES` (10) пользователей или больше половины активных, останавливается и пишет событие в журнал.
- Добавление и отключение пользователя запускают синхронизацию сразу; полная сверка идёт раз в час. Состояние последнего прогона видно администратору.

## Развёртывание

Отдельный PR с runbook. В документах только заглушки `<CF_HOST>`, `<DIRECT_HOST>`, `<TEAM>`, `<AUD>`.

- **`<CF_HOST>`:** Cloudflare Tunnel (`cloudflared` как сервис) на локальный порт MailExpert. TLS заканчивается на Cloudflare, входящие порты не открываются.
  - Access-приложение: self-hosted, один hostname, пустой путь.
  - IdP: только Google, Instant Auth включён, сессия 1 неделя.
  - **Ровно одна** Allow-политика: вторая молча расширяет доступ.
- **`<DIRECT_HOST>`:** DNS-запись без проксирования Cloudflare, reverse proxy на хосте. Сертификат — wildcard через DNS-01, чтобы имя хоста не появлялось в Certificate Transparency. Proxy отвечает только на `<DIRECT_HOST>`.
- Контейнеры слушают только loopback.
- В каждом Google-приложении для Gmail-ящиков и в OAuth-клиенте входа регистрируются redirect URI обоих хостов.
- После переименования team domain Cloudflare нужно поменять `CF_ACCESS_ISSUER` и пересоздать контейнер: старые токены проходят edge, но не проверку issuer.
- Режим `AUTH_MODE=google` включается в проде только после PR 3.

## Разбиение на PR

1. **Вход.**
   - `AUTH_MODE`, проверка JWT Cloudflare Access и прямой Google-вход;
   - поля `users.email` и `users.disabled_at`, `BOOTSTRAP_ADMIN_EMAILS`, проверка статуса на каждом запросе, закрытие WebSocket;
   - `APP_ALT_URLS`: origin WebSocket и redirect URI OAuth-ящиков по origin запроса;
   - отключение локальных входов в режиме `google`, удаление резервной отправки системных писем с рабочих ящиков;
   - экран входа и управление пользователями в админке.
2. **Сервер обслуживает ящики.**
   - подключение при старте с очередью;
   - вход, выход и WebSocket больше не трогают ящики;
   - sync только по одному ящику с защитой от повторов;
   - системные интервалы синхронизации.
3. **Общие данные.** Миграция таблиц, снятие фильтра по владельцу во всех запросах и в API плагинов, события и push для всех, фронтенд правил, блок-листа и контактов.
4. **Журнал.** Таблица, запись событий, admin API.
5. **Интерфейс.** Экран журнала, удаление ящика для всех пользователей, чистка личных настроек, которые стали системными.
6. **Синхронизация с Cloudflare Access.**
7. **Развёртывание и runbook** двух входов.
8. **Google-приложения.** Переписанные PR 2–5 из `2026-09-15-google-multi-app-design.md`:
   - «уже подключён» означает, что ящик с этим email есть в установке;
   - переподключение по id ящика доступно любому пользователю;
   - флаг `legacy` и проверки «чужой ящик» не нужны;
   - callback возвращается на хост, с которого начато подключение.

## Проверка

- Модульные тесты:
  - middleware с локальным JWKS: валидный токен, чужой `aud`, чужой `iss`, истёкший, заголовок без настроенного Cloudflare;
  - callback прямого входа: неизвестный email, `email_verified = false`, bootstrap-админ, отключённый пользователь;
  - защита последнего администратора.
- Smoke-тест миграции PR 3 на Postgres 16 с данными в старой модели: два пользователя, ящики у обоих, правило «для всех ящиков» с пересылками, блок-лист, одноимённые адресные книги, CardDAV-настройки у двоих, отложенное письмо. После миграции оба пользователя видят все ящики, правила и блок-лист размножены по ящикам, данные не потеряны.
- Тест `imapManager`: вход, выход и подключение WebSocket не вызывают подключение и отключение ящиков; повторный sync одного ящика пропускается.
- Тест журнала: отправка и удаление пишут записи без темы и текста; ошибка вставки не ломает действие.
- Ручная проверка:
  - два пользователя в разных браузерах через оба хоста;
  - отключение одного из них закрывает ему доступ сразу, а почта у второго продолжает синхронизироваться;
  - выход одного пользователя не прерывает синхронизацию.
