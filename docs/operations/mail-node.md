# Почтовый узел (mailcow)

Руководство для владельца: как поставить почтовый узел для ящиков на своих доменах и подключить его к
MailExpert. Выбор платформы и расчёты — в [исследовании](../architecture/mail-node-research/README.md),
требования к раскладке и переезду — в [дизайне развёртывания](../superpowers/specs/2026-09-21-deployment-design.md).

Плейсхолдеры: `<MAIL_HOST>` — имя почтового узла (например, `mail.example.com`), `<PANEL_IP>` —
публичный IPv4 сервера панели, `<DOMAIN>` — почтовый домен.

## 1. Кто что делает

**MailExpert:**
- создаёт домены и ящики через API mailcow и сразу подключает ящики по IMAP/SMTP;
- генерирует пароль ящика и хранит его зашифрованным; пароль никто не видит;
- при удалении ящика в MailExpert только отключает его в mailcow: почта на адрес отклоняется, письма
  остаются на диске;
- при повторном создании того же адреса включает ящик обратно с новым паролем, вместе со старыми
  письмами. Активный ящик, заведённый в mailcow руками, MailExpert тоже забирает себе: задаёт новый
  пароль. Старый пароль Dovecot помнит ещё до 5 минут (кэш входа `auth_cache_ttl`), а уже открытые
  сессии прежнего владельца смена пароля не рвёт. Чтобы отрезать их сразу, на узле:
  `docker compose exec dovecot-mailcow doveadm auth cache flush` и
  `docker compose exec dovecot-mailcow doveadm kick <адрес>`;
- даёт квоту 5 ГБ каждому новому ящику (меняется в настройках узла); квоту отдельного ящика
  администратор меняет в таблице ящиков. Квота диск не резервирует;
- раз в 10 минут читает заполнение диска с почтой и пингует ссылку проверки;
- не даёт менять сервер, логин и пароль ящика узла в его настройках: они берутся из настроек узла;
- если ящика уже нет в mailcow (удалён руками), удаление в MailExpert просто убирает строку.

Если узел не ответил на создание ящика (таймаут 15 секунд), ящик мог остаться созданным в mailcow
с паролем, которого никто не знает. Достаточно создать тот же адрес ещё раз: MailExpert заберёт его.

**Руками (этот документ):** установка mailcow, файрвол, DNS, Microsoft EOP, DKIM, бэкап узла.

## 2. Раскладка

Поддерживается **отдельный сервер для узла**: mailcow сам слушает 80/443 и выпускает сертификат
`<MAIL_HOST>`. Вариант «узел на одном сервере с панелью» пока не поддерживается: порт 443 там занимает
Caddy панели, а скрипты развёртывания не умеют проксировать на mailcow.

Требования к провайдеру узла (подробно — чек-лист в дизайне развёртывания, раздел 6):
- порт 25 открыт в обе стороны или открывается по заявке;
- PTR настраивается самостоятельно, IPv4 статический;
- NVMe, диск увеличивается без переустановки;
- IP не в блок-листах.

Сервер: Ubuntu 24.04, 4 vCPU / 8 ГБ для ~250 ящиков без антивируса (исследование, раздел 4).

## 3. Установка mailcow

1. DNS: A-запись `<MAIL_HOST>` на IP узла, TTL 300. PTR этого IP — `<MAIL_HOST>`.
2. Docker по [инструкции mailcow](https://docs.mailcow.email/getstarted/install/), затем:
   ```bash
   cd /opt && git clone https://github.com/mailcow/mailcow-dockerized && cd mailcow-dockerized
   ./generate_config.sh   # на вопрос об имени — <MAIL_HOST>
   ```
3. В `mailcow.conf`:
   - `SKIP_CLAMD=y` — антивирус делает EOP, экономия 1.5-3 ГБ памяти;
   - `SKIP_FTS=y` — MailExpert ищет по своей базе;
   - SOGo не отключать: отключение не поддерживается, без пользователей он почти ничего не тратит.
4. `docker compose pull && docker compose up -d`, войти в админку `https://<MAIL_HOST>/admin`,
   сменить пароль администратора.
5. Ключ API: «System → Configuration → Access → API», ключ **на чтение и запись**, в «Allow API
   access from» — только `<PANEL_IP>`. Ключ пока не закрывать, он понадобится в разделе 5.
6. Белый список блокировок: «System → Configuration → Options → Fail2ban parameters» → добавить
   `<PANEL_IP>` в whitelist. Панель ходит ко всем ящикам с одного адреса; без этого блокировка за
   неудачные входы одного ящика отрезала бы все.
7. Максимальный размер письма держать 25-35 МБ («Configuration → Options → Message size»).

Обновлять mailcow в течение нескольких дней после релиза (`./update.sh`): в админке регулярно
закрывают серьёзные уязвимости.

## 4. Файрвол узла

Docker публикует порты в обход `ufw`, поэтому правила для почтовых портов ставятся в цепочку
`DOCKER-USER`. Итог:

| Порт | Кому открыт |
|---|---|
| 22 | администратору (лучше по ключу и списку адресов) |
| 80, 443 | всем: выпуск сертификата; API закрыт списком адресов mailcow (раздел 3, шаг 5) |
| 25 | только диапазонам EOP |
| 587, 993 | только `<PANEL_IP>` |
| прочие почтовые порты (110, 143, 465, 995, 4190) | никому |

Диапазоны EOP берутся из веб-сервиса Microsoft: `https://endpoints.office.com/endpoints/worldwide?clientrequestid=<любой-uuid>`,
записи с `serviceArea: "Exchange"` и портом 25. Список меняется: сверять раз в месяц.

Пример через `iptables` (сохранить через `netfilter-persistent`):

```bash
# 587 и 993 — только панель
iptables -I DOCKER-USER -p tcp -m multiport --dports 587,993 ! -s <PANEL_IP> -j DROP
# 25 — только EOP: сначала разрешения на каждый диапазон, затем запрет остальным
iptables -I DOCKER-USER -p tcp --dport 25 -j DROP
iptables -I DOCKER-USER -p tcp --dport 25 -s <EOP_RANGE> -j ACCEPT   # повторить на каждый диапазон
# остальные почтовые порты закрыть
iptables -I DOCKER-USER -p tcp -m multiport --dports 110,143,465,995,4190 -j DROP
```

## 5. Подключение к MailExpert

«Настройки → Интеграции → Почтовый узел» (только администратор):
1. **Имя узла** — `<MAIL_HOST>`. Только имя, не IP: по нему идут IMAP, SMTP и API, поэтому переезд
   узла — это смена DNS.
2. **Ключ API** из раздела 3.
3. **Квота нового ящика** — 5120 МБ.
4. **Ссылка для проверки диска** — отдельная проверка в Healthchecks с интеграцией в Telegram:
   период 10 минут, grace 20 минут. Панель пингует успех, пока диск занят меньше чем на 85%, и
   `/fail` выше. Если узел недоступен или панель остановлена, пинги пропадают, и сервис пишет сам.
5. «Проверить и сохранить»: MailExpert читает список доменов и сохраняет настройки, только если
   узел принял ключ.

После этого в диалоге «Добавить аккаунт» у всех пользователей появляется «Ящик на нашем домене».

## 6. Новый домен

1. В MailExpert: «Почтовый узел → Новый домен», лимит ящиков (по умолчанию 500). Квоту домена
   MailExpert ставит с запасом (лимит × 100 ГБ), поэтому в неё ни создание ящика, ни увеличение квоты
   не упрутся; диск она не резервирует.
2. **Microsoft EOP** (исследование, раздел 2):
   - принятый домен `<DOMAIN>` в режиме **Internal Relay**;
   - входящий коннектор (EOP → узел) — smart host `<MAIL_HOST>`, не IP;
   - исходящий коннектор (узел → EOP) — по сертификату `<MAIL_HOST>`, не по IP.
3. **Relayhost в mailcow:** «Configuration → Routing → Sender-dependent transports» → транспорт на
   smart host EOP вашего тенанта (`<tenant>.mail.protection.outlook.com:25`), затем в настройках
   домена выбрать этот relayhost. TLS к EOP обязательный.
4. **DNS домена:**
   - MX → `<tenant>.mail.protection.outlook.com`;
   - SPF: `v=spf1 include:spf.protection.outlook.com -all`;
   - DKIM подписывает **одна** сторона: либо EOP, либо mailcow («Configuration → ARC/DKIM keys»).
     Решение пока открыто; двойная подпись не нужна;
   - DMARC: начать с `p=none` и отчётов, потом ужесточать.
5. Проверка: письмо снаружи на тестовый ящик доходит, ответ из MailExpert уходит через EOP
   (заголовки `Received`).

## 7. Бэкап узла

Бэкап панели (`backup.sh`) узел не покрывает. У mailcow свой скрипт:

```bash
MAILCOW_BACKUP_LOCATION=/opt/backup /opt/mailcow-dockerized/helper-scripts/backup_and_restore.sh backup all --delete-days 7
```

Запускать по cron раз в сутки и копировать `/opt/backup` к другому провайдеру (когда появится
S3-хранилище — туда же, куда бэкапы панели).

## 8. Переезд узла

Процедура — раздел 6 дизайна развёртывания: бэкап mailcow, `rsync` каталога vmail, заморозка
postfix и dovecot (входящую почту держит очередь EOP), восстановление на новом сервере, A-запись
`<MAIL_HOST>` на новый IP, файрвол по разделу 4, PTR. В MailExpert ничего не меняется: имя то же,
IMAP-соединения восстанавливаются сами. Коннекторы EOP, настроенные по имени и сертификату, тоже не
трогаются.

## 9. Проверить на первом узле

Связка MailExpert и mailcow проверена вживую скриптом `scripts/deploy/test/e2e-mailcow.sh`. Он
поднимает в одноразовом контейнере Docker-in-Docker mailcow `2026-09` и панель из опубликованного
образа, а затем через HTTP API панели проходит 11 проверок:
- неверный ключ API отклоняется, верный проверяется и сохраняется;
- домен создаётся из MailExpert;
- ящики создаются с квотой 5120 МБ и подключаются;
- письмо между ящиками доходит через узел;
- таблица квот и диск показываются, смена квоты доходит до mailcow;
- сервер ящика узла поменять нельзя;
- удаление отключает ящик, повторное создание включает его со старыми письмами;
- ящик, заведённый руками, перехватывается, и его старый пароль перестаёт работать;
- строка ящика, которого уже нет в mailcow, удаляется;
- адрес, который уже есть в MailExpert, отклоняется.

Запуск (нужно около 6 ГБ памяти для Docker, скачивает образы mailcow):

```bash
MSYS_NO_PATHCONV=1 scripts/deploy/test/e2e-mailcow.sh --image ghcr.io/wyrtensi/mailexpert-backend:sha-<12>
```

Что скрипт не покрывает и что проверить на первом боевом узле:
1. Доставка снаружи через EOP и отправка наружу через EOP (раздел 6, шаг 5).
2. Ссылка проверки диска получает пинги раз в 10 минут.
3. Настоящий сертификат `<MAIL_HOST>` от Let's Encrypt (в тесте — свой тестовый CA).
4. Белый список fail2ban для `<PANEL_IP>` (раздел 3, шаг 6).
